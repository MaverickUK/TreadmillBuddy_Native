# CLAUDE.md: context for working on Treadmill Buddy Native

This repo is the native C++ firmware for **Treadmill Buddy**: a Raspberry Pi Pico (RP2040) with a Pimoroni Pico Display Pack, controlling a treadmill through its 433 MHz remote's codes. It replaces the CircuitPython firmware in [MaverickUK/TreadmillBuddy](https://github.com/MaverickUK/TreadmillBuddy). That repo remains the behavioural reference: when porting or changing a feature, read the matching Python module first (`plan.py`, `code.py`, `ui.py`, `treadmill.py`). The structure follows [HDDSynth_Native](https://github.com/MaverickUK/HDDSynth_Native).

The owner is an experienced software architect (C#/.NET, TypeScript, Python) who is new to embedded C++. Explain embedded-specific decisions briefly, and favour clear, idiomatic code over clever code.

## Design rules

- **Core 1 is the treadmill and nothing else** (`treadmill.*`, `rf_tx.*`). It may block (RF bursts, press gaps, the START countdown). It must keep calling `link.beat()`, at least every `CORE1_STALL_MS`, or the watchdog resets the board.
- **Core 0 never blocks on the treadmill.** It only writes a `belt::Target` and reads `belt::Status`. Rendering only happens when the `View` changes and the previous DMA frame has finished.
- **Shared state lives in `TreadmillLink` only.** Each atomic has exactly one writer and uses only `load`/`store`: the RP2040's M0+ has no atomic read-modify-write instructions. Anything that must change as a whole is packed into one 32-bit word.
- **Keep the logic Arduino-free and host-tested:** `plan`, `app`, `belt`, `treadmill_link`, `canvas`, `screens`, `button`. Hardware stays in `main.cpp`, `treadmill.cpp`, `rf_tx.cpp`, `st7789.cpp`, `status_led.cpp`.
- **The plan must keep matching `plan.py`.** If plan behaviour changes deliberately, change both, and regenerate `test/native/plan_fixtures.h` with `test/gen_plan_fixtures.py`.
- **Safety:** a stop must always be able to interrupt (core 1 re-reads the target before each press). After a watchdog reset, boot sends STOP.

## Toolchain notes and gotchas

- **Build:** PlatformIO + Arduino-Pico (earlephilhower) via the maxgerhardt platform. On this machine `pio` is at `~/.platformio-venv/bin/pio`. Envs: `pico_28` (default) and `pico_114`, which differ by `-DDISPLAY_PACK`.
- **CPU clock:** `f_cpu` is 125 MHz so the LCD SPI is exactly 62.5 MHz. At 133 MHz it would fall back to 33 MHz. PIO's 1 µs tick is derived from `clk_sys`, so it adapts.
- **No float `printf`:** newlib-nano has no `%f`. Format tenths and hundredths as integers.
- **Core 1 starts before `setup()`** and runs concurrently, so core 0 must not touch the RF pin.
- **Fonts:** `src/fonts/*.h` are generated by `scripts/make_font.py` (Pillow) from `fonts/*.ttf` and committed, so builds and CI don't need Pillow. They're `const`, so they live in flash, not RAM.
- **RAM:** the 2.8" framebuffer is 150 KB of the RP2040's 264 KB (~162 KB used in total).
- **Tests:** `test/run_native_tests.sh` (ASan/UBSan). Run `SANITIZE=thread` too when touching `treadmill_link.h`.

## Versioning

SemVer in `src/version.h` (`FIRMWARE_VERSION`), starting at 0.1.0. Bump it in the same commit as any firmware change, and tag that commit `vX.Y.Z`. Push the tag on its own, after the branch.

## Status

Ported with feature parity to CircuitPython 1.2.0 (2026-10-21). It builds and the host tests pass. **Not yet run on hardware:** see the README's "First run on hardware" checklist (orientation, RF in test mode, a short bench session).
